# kabic migration

kabic (`~/Projetos/kabic`) reads C headers and their doc tags and describes them idiomatically in
C# and Zig. Its pipeline is a compiler: a C reader, a model, a classifier, writers. CΔ is its
evolution, with a richer model and more frontends and backends, so kabic is discontinued once CΔ
does its job.

CΔ does not port kabic (D166). kabic was designed for another context, and it adapts to CΔ, never
the reverse. Each piece below is a candidate: it is evaluated against CΔ's design, then redesigned
on CΔ's terms or discarded. kabic's code, tests and end to end suites are a source of cases and
of hard-won knowledge, not a specification, and matching kabic's output is not a goal.

## The doctrine, as a starting point

kabic's doctrine is the starting point of the C frontend and of every projection, kept
where it holds in CΔ:

- The C code already has semantics; what the AST says is read, never restated by a tag.
- Tags add only what C cannot say, state facts about a declaration, and never name a consumer.
- Writers spell semantics in their language and hold no other logic.
- A header that needs a tag to rebuild something is often the header to fix.
- Additional logic belongs in extensions that live with whoever needs them.
- The generic output is the goal, never a reproduction of earlier output.

## The clean room

The vocabulary of annotations is not taken from kabic's tags (D170). It is found by writing, by
hand and without reading kabic's output, the idiomatic CΔ projection of a slice of real APIs, and
asking for every difference from the raw import which fact the header did not say:

| API | Patterns it brings |
|---|---|
| KernelEngine | tables of function pointers with a `self` handle, owner pairs of a reference and a destructor, closures with a context, a library error enum |
| sqlite, through a manifest | a constructor and a destructor as a pair of free functions, an owned result freed by a given function, a callback over a counted sequence of optional texts, a callback whose return means continue |
| zlib | a length that goes in as a capacity and comes out as the count written, one error convention for the library |
| Vulkan | the two-call enumeration, output structs, handles destroyed with their parent, optional pointers, integers that are flags of an enum, structs extended by an `sType` and `pNext` chain, text in fixed buffers, sequences of texts, pointer and 64-bit handles, functions loaded at run time from a parent |

- A **fact** is true of the API in any language (this pointer owns, this function destroys it, these
  two parameters are one sequence) and becomes an `ann.` annotation. A **policy** is how one
  language chooses to show it (a class, an exception, a name style) and lives in the options of
  that projection, never in the IR.
- A fact enters the vocabulary only when it also means something in C#, checked by writing the
  C# form beside the CΔ one, even before a C# projection exists.
- Only then are kabic's tags and output read, as a list of cases the clean room may have missed,
  never as solutions to copy.

The CΔ projection comes first because CΔ consumes it: the std and every program get their C
libraries through it. A CΔ projection is valid C#, so the C# projection is the same shape with
a policy that swaps the std for the BCL (`Result` to exceptions or `TryX`, allocators to arrays,
UTF-8 `string` to `System.String`), made more idiomatic only after it works. Code written against
a library, such as a KernelEngine game, then has the same structure in CΔ and in C#. Both are
modes of `CDelta.Projection.CSharp`, which already emits the raw import stubs.

The raw layer of the C# projection is those stubs with what .NET needs (D107): `LibraryImport`
with the library's name instead of `extern` resolved by the C compiler, accessors in place of
`[Bits(n)]`, and a C shim, generated by `Backend.C` and built with the package, that exports each
`static inline` function and call-like macro the projection exposes.

## Candidates

Each row is evaluated before it is built; the right column is where the piece would land if it
survives.

| kabic | CΔ |
|---|---|
| `Kabic.Reader`: clang AST, doc tags, YAML annotations, constants | `CDelta.Frontend.C`: reading on libclang; tags and the annotation manifest as `ann.*` annotations ([compiler/ir.md](compiler/ir.md#annotations)) |
| `Kabic.Core`: `ApiModel`, `CType` | Delta IR declarations; `CType` is the IR type with C spelling |
| `Kabic.Core`: the slot classifier (owner, bag, vtable, factory) | `CDelta.Projection`: shared analyses over IR declarations used by every projection |
| `Kabic.Core`: `Convention` (name rules and type maps per language) | projection options, in a format designed for `cdc` |
| `Kabic.CSharp` writer | `CDelta.Projection.CSharp`, its CΔ projection mode first and its C# projection mode after ([the clean room](#the-clean-room)) |
| `Kabic.Zig` writer | `CDelta.Projection.Zig` |
| `Kabic.Bindings` (raw bindings through ClangSharp) | the raw layer of `CDelta.Projection.CSharp`, written from the IR as the import stubs are (D107) |
| `Kabic.Pipeline`, domains, regeneration, drift | `cdc project` command and its domain manifest |
| `Kabic.Factories` and other extensions | extensions loaded by `cdc project`, outside the core repository |
| checks (reconstruction, API coverage) | `cdc project --check` |

`CDelta.Projection` and the projections depend only on `CDelta.Ir`.

## The command

```bash
cdc project --manifest api_domains.json --lang cdelta --out src/cdelta
cdc project --manifest api_domains.json --lang csharp --out src/csharp
cdc project --manifest api_domains.json --lang zig --out src/zig
cdc project --manifest api_domains.json --check
```

A projection may also live outside the compiler, in any language, as a plugin (D167):

```bash
cdc project --manifest api.json --plugin ./cdelta-python --out src/python
```

`cdc` runs the plugin, writes to its standard input one request holding the declaration layer
of the IR (declarations, attributes and annotations), the analyses of `CDelta.Projection` and the
plugin's options, and reads from its standard output the files to write and any diagnostics. The
request and the response are JSON with a format version; their schema is published with the
compiler. A community writes the backend for its language in that language, without touching
CΔ's repository.

The manifest format is designed for `cdc`; kabic's format is not read. A one-time converter
from kabic's manifests may exist if it is cheaper than rewriting them.

## What CΔ gains

- CΔ imports can use the same tags: a projection for CΔ itself turns an `array_of` pair
  into a `Span<T>` overload and an `out` pointer into an `out` parameter, on top of the raw import.
  This is optional and layered; the raw import of [language/c-interop.md](language/c-interop.md)
  stays the default.
- CΔ exports go through the same projections, so a library written in CΔ gets C#, Zig and
  CΔ bindings of its exported surface from the same tool.

## Order

1. CΔ reaches milestone M5 (C import) of the [roadmap](roadmap.md): the C frontend reads
   declarations, layouts, constants and comments.
2. Run [the clean room](#the-clean-room) and record the vocabulary of facts it finds.
3. Review every candidate above against CΔ's design and that vocabulary, and record what is kept,
   changed or dropped, before any of it is built; the review is a gap review like those of the
   milestones.
4. Build the annotations of the C frontend, `CDelta.Projection` and the CΔ projection, then the C#
   projection and the Zig projection, taking kabic's tests as cases where they still apply.
5. Run the end to end suites (probe, zlib, sqlite, vulkan) through `cdc project`. They must
   compile and pass their runtime checks; their output is CΔ's, not kabic's.
6. Switch KernelEngine to `cdc project`. Until then kabic stays untouched and in use.
7. Archive kabic.

No change is made in the kabic repository during the migration; it keeps serving its consumers
until step 7 succeeds.
